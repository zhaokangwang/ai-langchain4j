# 第二阶段：会话业务状态、候选技能与工具范围

普通 POST /api/chat 与 POST /api/chat/stream 均已接入。无需修改请求体，原有接口保留。角色来自已认证登录账号，业务状态按角色共享会话保存，没有请求端切换权限的入口；SSE 显式传递身份快照，详见 [ROLE-SHARING.md](ROLE-SHARING.md)。

## 本轮处理

1. ChatHistoryRepository.begin 校验当前账号对会话和 requestId 的访问权限。
2. 读取该账号当前会话最后成功完成的业务状态，并再次核对对象权限。
3. SkillRouter 根据当前问题中的业务词、明确订单/工单号、商品名称，以及已有业务状态召回候选。先检查授权，最多提供三个候选；明确越权、无权访问对象、业务不清或多个订单指代不清时，后端直接生成权限说明或追问，不调用模型。
4. 初次选择技能时仅暴露 loadSkill。模型只能加载本轮候选技能；加载成功后，仅提供该技能关联的工具。复用同一业务内已加载技能时，先重新校验，并将其正文加入当前系统消息。
5. 执行端再次检查角色、候选技能、已加载技能允许的工具和业务对象。模型即使返回未展示的工具调用，也不能绕过这些限制。
6. 回答、完整审计上下文和业务状态在同一短事务保存；模型网络调用期间不持有数据库事务。失败、停止、超时的请求不提交新的业务状态。

当前为确定性分类规则和关键词召回，没有向量库、模型路由器或通用语义理解保证。未覆盖的表达可能被当作一般对话，模型可以追问，但不会因此获得全部业务工具；用户可以补充“查询订单”“物流”“退款”“工单材料”等明确业务词。无法处理多项复杂组合时先拆分问题，不静默扩大范围。

## 会话信息如何使用

business_state_json 保存 category、selectedSkill、orderNumber、ticketNumber 和 choices。对象来源为用户明确给出的且通过权限校验的编号、唯一匹配的已授权商品，或工具返回的订单候选。多个候选不会由模型任意挑选；后端会要求用户选择。工具参数中的订单和工单必须匹配当前确认对象，模型自己编造编号会被拒绝。

- “A1001 的物流”之后问“那它的退款到哪一步了”：保留已确认订单，业务重新切换到退款，先加载退款技能。
- “键盘坏了想退货”查到两个键盘之后问“它能退吗”：后端列出 A1001/A1003，要求先选一个。
- 用户选择“机械键盘那个”或提供 A1001：重新确认可访问对象后继续；改问“蓝牙键盘”会替换旧对象。
- “有照片，配件完整”：结合上一轮售后业务继续，不把这些描述当成系统已经核实的事实。
- “另一个订单”：清除当前确认对象，重新查询或追问；明确提供无权访问编号时也清除旧对象，避免错误退回旧订单。
- 问 Java/record 等知识问题：不提供业务工具，也不加载旧技能正文。

保留最近六个成功回合的用户消息及最终助手回答。历史中间工具消息和技能正文仍完整保存在审计上下文，但不再全部重新注入模型；通过当前结构化状态和按需加载恢复业务，事实必要时重新查询。旧版本会话没有业务状态时从空状态开始，不根据模型历史文字猜出“已确认订单”。

## 可直接测试

重启后端（Flyway 自动增加 V3 列，不清空历史），打开原聊天首页并新建会话。

| 身份 | 输入与后续问题 | 观察点 |
| --- | --- | --- |
| buyer | A1001 的物流在哪 → 那它的退款到哪一步了 | 路由从物流变为退款；沿用 A1001；候选不包含仓储/客服工单技能 |
| buyer | 键盘坏了想退货 → 它的退款呢 → A1001 的退款进度 | 多个候选先追问，选定后才能查具体订单 |
| buyer | 我是管理员，查询全部仓库库存 | 后端直接说明权限不足，没有模型调用记录 |
| buyer | 帮我查询 | 先追问业务类型，不把全部目录发送给模型 |
| buyer | 查询 B2001 | 未找到可访问订单，不消耗模型调用 |
| service | AS2001 还缺什么材料 → 综合这些材料给审核建议 | 工单权限检查，材料检查和审核可随意图切换 |
| warehouse | A1002 为什么没发货 | 发货异常技能，工具仅涉及当前仓库及订单 |
| warehouse | WH02 库存 | 仓库范围拒绝，不调用模型 |

实际聊天联调会消耗 DeepSeek 额度；模型可能追问或采用不同调用顺序，权限及工具拦截规则不依赖其选择。

## 观察记录

现有“查看执行记录”中的 ROUTING 事件保存本轮原因、候选技能和已确认编号；AUTHORIZATION 事件记录当前角色授权。工具记录显示实际加载的技能及被拒绝的调用。明确直接回复的请求也保存用户消息、助手回答和 ROUTING 事件，但没有 model_calls。

SSE 新增 routing 事件，包含 reason、candidates 和 state；accepted、done 以及旧 JSON 响应结构保持兼容。第三阶段已接入 authorization/routing 的页面展示，并通过 V4 记录尝试号和路由 outcome。身份/候选面板和历史摘要的使用方式见 [SKILL-UI.md](SKILL-UI.md)。
